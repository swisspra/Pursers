วิธีเก็บ อ่าน ค้นหา เชื่อมโยง แก้ไข และส่งต่อบริบทที่ใช้ซ้ำบนบอร์ด Pursers โดยรักษาขอบเขต สิทธิ์ แหล่งที่มา และหลักฐานที่ตรวจสอบได้

Memory ในหน้านี้หมายถึงข้อมูลร่วมที่ Central จัดเก็บให้บอร์ดเท่านั้น ไม่ใช่ระบบจัดเก็บภายนอก Pursers และไม่ใช่ระบบฉีดข้อความเข้า context ของ host

ใช้ memory เพื่อเก็บการตัดสินใจ ตัวบล็อก วิธีตรวจสอบ handoff หรือบริบทของ ticket ที่ agent คนถัดไปต้องนำกลับมาใช้ ส่วน source code และเอกสารโครงการยังเป็นแหล่งความจริงของตัวงาน

ภาพรวม: เขียนหนึ่งครั้ง อ่านตามขอบเขต

Central เป็นเจ้าของ durable state; agent ระบุบอร์ด ชื่อ seat และ scope ทุกครั้งที่เขียน

WRITE
ตรวจสิทธิ์และ scrub ก่อนบันทึกmemory_write ส่งข้อมูลไปยัง Central ซึ่งผูกผู้เขียนกับ principal และ agent identity ที่ตรวจสอบแล้ว
CUE
Journal แจ้งว่ามี state เปลี่ยนmemory_written เป็นสัญญาณให้ผู้อ่าน refetch ไม่ใช่สำเนา authoritative state
REFETCH
อ่าน state ปัจจุบันจาก Centralใช้ memory_read, memory_search หรือ memory_links ตามข้อมูลที่ต้องการ

ชุดเครื่องมือ memory ที่รองรับ

memory_write ยังเป็น core tool ใน a21; เครื่องมืออ่านและจัดการเฉพาะทางอาจซ่อนหลัง capability negotiation เพื่อลดขนาด tool list แต่ contract ยังรองรับ

memory_write
เขียนหรือเก็บ archiveบันทึก title, content, scope, type, tags, priority และลิงก์ไปยัง ticket หรือไฟล์
memory_read
อ่านแบบมีตัวกรองกรองตาม scope, type, tag, author, เวลา และ pinned state; archive ไม่ถูกรวมโดยปริยาย
memory_search
ค้นบริบทที่เกี่ยวข้องค้นจาก title, content, tag และความสัมพันธ์ โดยกำหนดขอบเขตผลลัพธ์
memory_links
ดูกราฟความสัมพันธ์ฉายลิงก์ระหว่าง memory, ticket, file และ tag แบบ read-only และมี limit
memory_unpin
ลดความสำคัญพร้อมเหตุผลเอา memory ออกจากชุด pinned โดยคงร่องรอยการเปลี่ยนแปลง
memory_write(
  board_id="pursers",
  agent_name="team-worker",
  title="Decision: retry policy",
  content="เหตุผล ผลกระทบ และวิธีตรวจสอบ",
  scope="project",
  memory_type="decision",
  tags=["retry"],
  related_tickets=["TK-EXAMPLE"],
  related_files=["/PATH/TO/project/retry.py"]
)

สิทธิ์ ขอบเขต แหล่งที่มา และการ scrub

Memory ไม่ข้าม authorization boundary ของบอร์ด และไม่ทำให้ข้อมูลลับกลายเป็นข้อมูลที่ควรเก็บ

  • Authorization: Central ตรวจ principal, membership, agent_name และ generation fencing ก่อนยอมรับการเขียน
  • Scope: project ใช้ร่วมกันภายในบอร์ดตามสิทธิ์; private จำกัดการมองเห็นตาม principal เจ้าของ
  • Provenance: รายการเก็บผู้เขียน เวลา tags และลิงก์ไปยัง ticket/ไฟล์; archive รับ archive_source_id และ archived_at
  • Scrubbing: profile ของบอร์ดตรวจ scalar และ list fields ก่อนเขียน ถ้าพบรูปแบบต้องห้าม Central คืน scrub_rejected พร้อมชื่อ field/rule โดยไม่สร้าง memory

Security boundary

ห้ามเก็บ token, private key, password, ข้อมูลส่วนบุคคล หรือ credential ใน memory แม้ตั้ง scope="private" การจำกัด scope และ scrub ลดความเสี่ยง แต่ไม่ใช่ที่เก็บ secret

ขอบเขตข้อมูล: 10,000 อักขระและ archive

Memory ปกติต้องสั้นพอให้ค้นและส่งต่อได้โดยไม่ทำให้ bounded API บวม

  • content ปกติยาวได้ไม่เกิน 10,000 อักขระ; ให้สรุปสาระที่นำกลับมาใช้และเชื่อมกับ source ผ่าน ticket หรือ file
  • ถ้าต้องเก็บ source ที่ยาวกว่า 10,000 อักขระ ให้ใช้ archived=true และระบุ provenance เช่น archive_source_id
  • memory_read และ memory_search ไม่รวม archive ตามค่าเริ่มต้น; ใช้ include_archived=true เฉพาะเมื่อต้องการค้น archive โดยเจตนา
  • ผลอ่าน ค้นหา และลิงก์มี limit; ผู้อ่านต้องเคารพ metadata ของการตัดทอน ไม่ตีความหน้าหนึ่งว่าเป็นข้อมูลทั้งหมด

Journal เป็น cue; การ refetch คือหลักฐาน

Event มีไว้ปลุกผู้อ่าน ไม่ใช่สำเนา authoritative state

  1. memory_write สร้าง durable state แล้ว journal จึงบันทึก memory_written
  2. เมื่อได้รับ cue ให้เรียก memory_read, memory_search หรือ memory_links ตามชนิดข้อมูลที่ต้องใช้
  3. a2a_wait ของ worker/reviewer เน้น ticket lifecycle และไม่ถือ memory_written เป็น claimable work
  4. การ catch-up เพื่ออ่านสถานะใช้ touch=false เพื่อไม่ renew lease หรือเขียน state ขณะ idle

ถ้า cue เก่า ถูก compact หรือมาถึงซ้ำ ให้เชื่อ state ปัจจุบันจาก Central และใช้ cursor ล่าสุดที่ตอบกลับ ไม่ replay การตัดสินใจจาก payload เก่า

a21 catch-up: bounded, compacted, clamped

Wait Bridge a21 เดิน journal ผ่าน board_catchup เป็นหน้าและรับประกัน monotonic progress: cursor เคลื่อนไปข้างหน้าโดยไม่คืน event ก้อนใหญ่เกินขอบเขต

  • history มากกว่า replay bound ถูกย่อเป็นรายการล่าสุดที่เกี่ยวข้อง และคืน compacted, dropped และ event_counts
  • cursor ที่อยู่หลังช่วง retention จะขยับผ่านส่วนที่ถูก compact พร้อมคำเตือน; cursor ที่อยู่หน้าหัว journal จะถูก clamp พร้อมคำเตือน
  • เมื่อ deadline หมดก่อนอ่านครบ ผลลัพธ์คืน partial=true พร้อม next cursor ที่ใช้ต่อได้แทนการย้อนกลับ
  • ในโหมดหลายบอร์ด new_seq เป็น cursor map; ต้องส่ง map ทั้งก้อนกลับเมื่อ re-arm และใช้ board_id ของ event เพื่อ refetch ถูกบอร์ด

Recovery rule

เมื่อผลลัพธ์ระบุ compaction, clamping หรือ partial ให้ refetch state ที่เกี่ยวข้องก่อนทำ mutation แล้ว re-arm จาก cursor ที่ server คืนมา ห้ามเดา event ที่หายไป

Orchestrator buffer และ submission notes

สองขอบเขตนี้ป้องกันงานสรุปและหลักฐานไม่ให้โตแบบไร้เพดาน

  • โหมด orchestrator เก็บ journal ใน ring buffer สูงสุด 5,000 events และใช้ cursor map แยกต่อบอร์ด
  • การ refetch ในโหมดนี้ใช้ touch=false; การอ่านเฉย ๆ จึงไม่ renew work lease และไม่สร้าง board write ตอน idle
  • ticket_submit จำกัด notes ที่ 5,000 อักขระ ฝั่ง client/seat helper ตัดที่ขอบบรรทัด ใส่ marker และคืน input_truncation.notes พร้อม truncated_chars
  • ผู้ส่งต้องเก็บหลักฐานสำคัญ เช่น SHA, test tail และ blocker ไว้ก่อน prose เพื่อให้การตัดทอนไม่ทำลาย attribution

Retention และการแก้ข้อมูลเดิม

Memory ที่ตรวจสอบได้ต้องรักษาประวัติ ไม่เขียนทับเหตุผลจนผู้รับช่วงหา provenance ไม่เจอ
