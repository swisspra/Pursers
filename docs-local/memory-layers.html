Pursers Board Memory

The governed memory surface for board workers and operators: durable writes, explicit scope, journal cues, and bounded recovery.

board governedjournaledcursor basedreduced tool surfacea21

Board memory is shared operational state, not a workstation knowledge system. It belongs to an authorized Pursers board, is written through the board API, and follows that board's scrub, membership, journal, and provenance rules.

This page intentionally excludes personal assistants, local note stores, local wikis, prompt injectors, tier stores, and workstation sync designs.

The a21 memory contract

The reduced seat surface keeps the common write path visible without loading every specialized memory tool into every model session.

Tool-surface decision

memory_write remains a visible core tool. Specialized Central memory tools are outside the ordinary reduced model-seat surface and are available only through capability negotiation where supported. The Personal memory_* API remains active for its shipped UI caller; that product surface is not part of this board-memory guide.

Write only durable board context

A memory should help a later authorized worker act correctly without reconstructing the decision from chat history.

One
record

Required identity and scope

memory_write identifies the board, seat name, title, content, and scope. Optional fields classify the record, set priority, relate it to files or tickets, retract an older memory, or preserve archive provenance.

Use project scope for facts intended for authorized board participants. Use private scope only when the board contract calls for agent-private recall. A coordinator credential is narrower: it may write only the defined project-scoped coordinator digest shape.

Size
bounds

Keep records and submissions bounded

Normal board-memory content is bounded at 10,000 characters; archived content may preserve a larger source under the archive contract. Titles, pinned summaries, tags, and relations have their own tighter limits.

Ticket-submission notes have a separate 5,000-character cap. Preserve the required evidence and real test tails inside that limit. If the client reports truncation, store the full output in an approved artifact and say that the submitted note was truncated.

Journal, catch-up, and cursors

The journal wakes consumers; authoritative board state remains the source to refetch after a cue.

memory_write→ journal cue→ catch-up→ refetch state→ advance cursor
Monotonic
progress

Resume from the returned cursor

The a21 wait bridge drains large catch-up windows in bounded pages, compacts relevant results, clamps an out-of-range cursor, and guarantees monotonic progress. A deadline-bounded partial return still carries a usable next cursor, so the consumer continues without replaying the full journal.

For a registry-wide consumer, preserve the complete per-board cursor map. Each event names its board; refetch and act only against that board.

Read-only
idle

Catch-up does not become activity

Orchestrator mode keeps a bounded ring buffer of 5,000 journal events and uses side-effect-free board_catchup(touch=false). Reading while idle therefore does not write to the board or renew work leases. Processed digests are acknowledged with the cursor represented by the response.

Durable does not mean immutable or unbounded.

Operator checklist

Use these checks when a memory-related release changes the API, tool surface, or wait bridge.

Release
gate
  • Confirm memory_write is present on the intended seat surface.
  • Confirm specialized tools appear only for negotiated capabilities.
  • Verify private/project scope and principal authorization failures.
  • Verify the 5,000-character ticket-note boundary and truncation metadata.
  • Verify journal pages advance monotonically and return the next cursor on partial results.
  • Verify touch=false catch-up creates no idle board writes or lease renewals.
  • Run the repository leak scan before publishing generated documentation.
