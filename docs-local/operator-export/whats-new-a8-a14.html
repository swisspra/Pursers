1. Coordinator — ตัวคุมวงกลาง (ACTIVE)

ชิ้นสุดท้ายจาก north-star: daemon ที่เฝ้าทุกบอร์ดใน registry แล้วทำงานแทนคุณ 3 ชั้น

Phaseทำอะไรสถานะ
1 — Findingsตรวจ: งานจอด (starved), claim ค้าง/หมดอายุ, review backlog, งานปิดแล้วไม่ merge (closed-but-unmerged), บอร์ดเสื่อม (degraded), privacy leak (จากไฟล์คำต้องห้าม private) — ทุก finding มี evidence + next_action บอกว่าต้องทำอะไรต่อรันอยู่
2 — Dispatchงานจอดครบ 30 นาที → nudge seat ที่ว่าง · ครบ 60 นาที → force-assign ให้ seat ที่ภาระน้อยสุด (ไม่รอคน ตามที่เคาะ) · atomic ผ่าน ticket_assign ใหม่ใน central · มี rate limit + circuit breaker ถอยกลับ shadow เองACTIVE
3 — Intakeรับ "คำสั่งหนึ่งบรรทัด" จาก board_state key coordinator_intake → แปลงเป็น ticket เต็มรูป · auto-create เฉพาะ docs/tests/read-only/bug-มี-repro บน domain personal · ที่เหลือ + ทุกอย่างฝั่ง work = draft รอคุณ approve · ปิดเป็น default (--enable-intake)โค้ดครบ (ปิด default — เปิดเมื่อ grant board:intake)

คำสั่งรัน (ปัจจุบัน daemon รันอยู่แล้วบนเครื่องนี้)

CUT=/PATH/TO/local$CUT/pursers-personal-app/.venv/bin/python \
  "MCP Server/Pursers-local/tools/coordinator/coordinator.py" \
  --url https://127.0.0.1:8766/mcp \
  --token-path $CUT/.private-arm/jwt/tokens/principal-a.jwt \
  --home-board pursers --agent-name coordinator-1 --poll-seconds 60 \
  --integration-watch-since 2026-08-27T00:00:00Z \
  --mode active        # kill switch: เปลี่ยนเป็น --mode shadow แล้ว restart
Watermark 2026-08-27 ตัด false positive จากการ rewrite git history — ticket ที่ปิดก่อนวันนั้นถูก suppress แบบมีตัวเลขให้เห็น (ไม่หายเงียบ)

ผลงานจริงวันแรก

  • จับ closed-but-unmerged จริงบนบอร์ด work 5 ใบ (TK-4abd76e3…, 4d23793c…, 66705b78…, 880b0bbb…, e98944be…) — รอคุณ merge ตาม flow ฝั่งงาน
  • จับ ticket rename เก่าของ pursers ที่ปิดแล้วลืม merge (จัดการแล้ว)

เปิดใช้ intake เมื่อพร้อม (2 ขั้น)

# 1) grant capability แคบให้ principal ของ coordinator (คุณรันเอง — เป็น membership write)
#    scope ใหม่: board:intake  (สร้าง ticket + เขียนเฉพาะ intake keys เท่านั้น — ทุกอย่างอื่นถูกปฏิเสธ)
# 2) restart coordinator เพิ่ม --enable-intake  (และ/หรือเปิดสวิตช์ในหน้า /config)

2. Fleet Dashboard — dashboard หลัก (webapp)

ทิศทางที่เคาะ: webapp เป็นตัวหลัก / MCP App เป็น inline per-project — เปิดที่ http://127.0.0.1:8899

ONBOARD_CENTRAL_TOKEN=$(cat $CUT/.private-arm/jwt/tokens/principal-a.jwt) \
  $CUT/pursers-personal-app/.venv/bin/python \
  "MCP Server/Pursers-local/tools/fleet-dashboard/fleet_dashboard.py" --port 8899
  • หน้าแรก: pool summary (online/busy/available/stale — busy มาจาก agents projection ของ central ไม่ใช่เดาจาก ticket), การ์ดต่อบอร์ด, ticket counts (ขึ้น ≥ เมื่อโดน truncate — ไม่โกหกว่าเป๊ะ)
  • Board drill-down: ตาราง ticket ทุกสถานะ กดขยายดู description/submission/review + activity feed
  • Agent drill-down: seat อยู่บอร์ดไหน role อะไร ถืองานใบไหน
  • Timeline / Changes / Flow (port จาก v4): activity รายวันต่อ ticket · "มีอะไรเปลี่ยนใน 24 ชม." · pipeline คอลัมน์ open→claimed→submitted→closed · กด / เพื่อ filter
  • Coordinator findings panel: แสดง evidence + next_action สีตาม level บนหน้า board detail
  • /api/overhead: token overhead ต่อ seat (ดูข้อ 9)
  • หน้า /config: policy ทุกตัวของ coordinator ในหน้าเดียว — thresholds, always-ask/auto matrix, watermark, intake toggle — เขียนผ่าน CAS (กันทับกัน) ลง board_state; coordinator อ่านสดทุก poll; mode แสดง read-only (เปลี่ยนต้อง restart)

วินัยเดิมครบ: loopback-only · read-only (ยกเว้น config key เดียวที่กำลังเพิ่ม) · ทุก call bounded · ไม่ hardcode ชื่อโปรเจกต์

5. pursers-worker — worker จาก API (LiteLLM/OpenAI-compatible)

Runtime สำเร็จรูปสำหรับ worker ที่ไม่ใช่ CLI agent: อ่าน config ไฟล์เดียว (endpoint, model, key จาก env/ไฟล์ 0600, seat) แล้ววน wait→claim→ทำงาน→submit เองครบ

  • เครื่องมือถูกขังใน work_dir (path escape ถูกปฏิเสธ), timebox ต่อคำสั่ง, max 40 iterations
  • Governance เท่า worker อื่นทุกประการ — ผ่าน reviewer เสมอ, ไม่มีสิทธิ์ merge
  • system prompt เรียงแบบ cache-friendly (directive นิ่งอยู่หน้า)
เหตุที่ต้องมี: config ของ codex CLI เป็น global ตัวเดียว — ชี้ endpoint อื่นจะพัง reviewer ที่แชร์อยู่ · ตัวนี้คือ shape เดียวกับ "agent pool containers" ในภาพ enterprise ที่จะเสนอทีมงานด้วย · รอจากคุณ: endpoint + key ของ LiteLLM แล้วผมทำ config + seat ให้ (README: tools/worker-runtime/README.md)

7. Release อัตโนมัติ + Reproducible builds

  • Push tag v* ครั้งเดียว → GitHub Release สร้างเอง (wheels 6 ตัว + SHA256SUMS + notes จาก CHANGELOG, mark Latest) — ใช้จริงแล้วตั้งแต่ a8 คุณไม่ต้องกดเองอีก
  • PyPI publish: gh api …/publish-pypi.yml/dispatches -f ref=main — ตอนนี้ build ด้วย toolchain pinned + sha gate เทียบ component-lock ก่อน upload (บั๊กที่เจอ: CI เคย build ด้วย setuptools ไม่ pin ทำให้ wheel บน PyPI ไม่ตรง lock ตั้งแต่ a4 — แก้แล้ว + พิสูจน์ byte-identical)
  • pip install pursers จาก PyPI ล้วนๆ ผ่าน verify_component_artifacts แล้ว — ครั้งแรกของโปรเจกต์
  • ระวัง: component ที่ publish ไปแล้วก่อน fix (เช่น client a12) ไฟล์ immutable — ถ้า lock ต้อง match ให้ bump version publish ใหม่ (เหตุที่มี client a13 ทั้งที่ source เท่าเดิม)
