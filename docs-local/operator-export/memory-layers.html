Four-Layer Memory Store

How persistent memory is arranged for a coding agent on a single workstation — what auto-loads, what waits to be read, and what never leaves the machine.

4 layers2 isolated domainsgit-versioned subsetlocal-first

The whole design turns on one balance. Every session auto-loads a small block of text. Put too little in it and the deeper tiers are never reached — the agent doesn't know they exist, so they die unread. Put too much in it and every session starts bloated, and the store dies of context cost instead.

So the auto-loaded file carries only guardrails, working style, and a pointer. Bulk facts live one level down and are read when a task makes them relevant.

The four layers

Each layer answers a different question: what loads always, what the agent can reach for, what belongs to one project, and what survives a rebuild.

Layer 1
InjectorA lean file that auto-loads into every session. Policy only.
Layer 2
Tier storeDurable facts sorted into four tiers, read on relevance.
Layer 3
Per-project memoryOne fact per file, indexed, scoped to a single working directory.
Layer 4
SyncA git allowlist that versions the portable subset and nothing else.

Layer 1 — The injector

The only file guaranteed to be in context. Everything else has to earn its way in.

Always
loaded

Lean by construction

~/.claude/CLAUDE.md

This file is treated as a system-prompt layer, not a knowledge base. It holds four things and refuses the rest:

  • Pinned guardrails — the rules that must never be crossed
  • Working style — concision, verification habits, when to ask instead of guess
  • Account context — which identity belongs to which kind of task
  • A pointer — where the real facts live, so the agent knows to look

The rule of thumb: if a fact is only needed for some tasks, it belongs in the tier store, not here.

Layer 2 — The tier store

Durable memory, sorted by how permanent it is and which domain it belongs to.

Read on
relevance

Four tiers, one source of truth

~/.claude/memory/

0-core/       L0   principles, guardrails, policy, durable facts
                  source of truth; facts can be retired or refreshed
1-main/       L1   per-session working memory; consolidation lands here
2-work/       L2.1 professional domain
2-personal/   L2.2 everything outside it

An index file inside 0-core/ is the way in: a grouped, one-line-per-fact table of contents pointing at every file in the store. It is what the agent scans when the pointer in Layer 1 sends it here.

Injection flow

L0 core → always→ L1 working + L2 domains   ·  L1 → rarely→ L2

Core reaches everything. Session memory rarely needs to reach the domains — and when it does, it is a deliberate promotion, not a default.

Hard separation — never crossed

The two domain tiers do not mix: not data, not memory, not context, not deliverables. A tool or account authorised for one domain is never used for the other. This is the one rule the injector spends its scarce space restating in full, because a violation here is not recoverable by cleanup.

Promotions run upward with review: something learned in a session sits in 1-main/ until it proves durable, then moves into 0-core/ as a fact.

Layer 3 — Per-project memory

Facts that only make sense inside one working directory, kept beside that project's session history.

Scoped to
one project

One file, one fact, one index

~/.claude/projects/<project-key>/memory/

The project key is the working directory path with every non-alphanumeric character replaced by a dash — so the same folder always resolves to the same memory, and a renamed or moved folder resolves to a new one.

Each memory is a single markdown file carrying a small front matter block:

---
name: short slug
description: one line — used to judge relevance during recall
type: user | feedback | project | reference
---

The fact. For feedback and project types, followed by:
**Why:**            the reasoning that makes it stick
**How to apply:**   what to actually do differently

The four types divide the space cleanly: user is who the person is, feedback is guidance they have given, project is ongoing work not derivable from the code, and reference is a pointer to something external.

Files cross-link with double-bracket wiki links. A link to a memory that doesn't exist yet is fine — it marks something worth writing later rather than a broken reference.

Alongside them sits MEMORY.md, the index actually loaded each session — one line per memory, title plus a hook, and never any content of its own:

- [deploy commands](reference_deploy_commands.md) — all run from repo root; three named scripts
- [naming convention](feedback_agent_naming.md) — role plus model goes in the name, not the platform field

What deliberately does not go here: anything the repository already records — code structure, past fixes, commit history, or the project's own instructions file.

Layer 4 — Sync

A small script versions the portable subset. The interesting part is everything it refuses to touch.

Versioned
subset

Allowlist, not blocklist

~/.claude/memory-sync.sh  ·  status | push [msg] | pull

The ignore file starts by excluding the entire directory, then re-includes only what is safe and mergeable. Inverting the default this way means a new file added by a future release is ignored until someone deliberately allows it — the failure mode is a missing file, never a leaked one.

# 1) ignore everything at the root
/*

# 2) re-include the safe subset
!/CLAUDE.md          the injector
!/settings.json      preferences and permissions
!/memory/            the tier store
!/agents/            agent definitions

# 3) per-project: keep each memory folder, drop everything else
!/projects/*/memory/

# 4) defense in depth — never tracked even if re-included above
**/*.jsonl           session transcripts
.credentials.json    tokens
*.local.json         machine-specific overrides

Session transcripts, authentication state, caches and runtime bundles stay on the machine. What travels is the part a second machine could actually use: policy, preferences, facts, and project memory.

Why the order matters

The layering is not housekeeping. Reading order decides which instruction wins; load order decides what every session costs.

Reading
order

Precedence resolves without guessing

Each layer answers a narrower question than the one above it, and they are read in that order. Two pieces of guidance that disagree therefore have a settled winner — the agent never picks arbitrarily.

1st
GuardrailsAbsolute. Nothing further down may relax them.
2nd
Working styleHow to proceed wherever the guardrails leave room.
3rd
Project memoryBeats general facts inside its own directory.
4th
Domain factsApplied when nothing more specific has spoken.

The prose is written to match the rank. The injector is imperative — rules, in the second person. Tier files are declarative — facts, dated, retractable. Project memory is corrective — what to do differently here, and why. A file’s voice tells you its authority before you have read a word of the content.

This is also why the store holds one fact per file. A file that argues two things cannot be cleanly outranked, retired, or refreshed — and it forces a reader to load both to use either.

Load
order

A stable prefix is a cheap session

Prompt caching matches on an exact prefix, evaluated in a fixed order: tool definitions, then system text, then the conversation. A hit requires every byte ahead of the breakpoint to be identical to last time — so the first thing that changes invalidates everything after it.

tools→ injector→ index  │  facts, on demand→ this turn

Left of the divider is written once and edited rarely — that is the cached prefix. Everything volatile is deliberately kept to the right of it.

Three properties of the layout fall out of that constraint:

  • The injector is small and near-frozen. Guardrails and working style change on the order of months, so the prefix stays byte-identical and sessions open on a cache hit rather than a full write.
  • Facts arrive late, as results. Reading a tier file mid-session appends to the conversation instead of rewriting the front of it — so recall extends the cache rather than busting it.
  • Growth is append-shaped. A new memory is a new file plus one index line. Nothing that already sits in the prefix gets rewritten, so yesterday’s cache still matches today.

The anti-pattern is the obvious one: inline every fact into the auto-loaded file. It looks simpler and costs twice. Each memory edit rewrites the prefix, so the next session pays a cache write instead of a read — and the accumulated bulk is then re-sent on every turn of every session, forever.

The asymmetry is what makes it worth designing around: a cache read bills at roughly a tenth of the base input rate, while a write bills at a premium above it. Invalidation is not a wash — it is paying full freight for text you had already bought.

Both payoffs come from the same property. Separating durable policy from volatile facts is what gives precedence a fixed order, and it is what keeps the front of the request still enough to cache.
