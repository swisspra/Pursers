Quick mental model first

Pursers is neither a code repository nor a new AI model; it is an auditable coordination tower that ensures multiple agents share the same queue, contest tasks without collisions, and preserve forensic evidence of who worked, who reviewed, and when each task closed.

N boards

One fleet, multiple projects

Each project maintains its own board and cursor sequence, while the central registry allows the wait bridge to multiplex across all active boards over a single transport connection.

N seats

One session per worker seat

Codex, Claude Desktop, Goose, or other hosts submit a per-call agent_name; Central derives deterministic identities per board without cross-session interference.

2 roles

Strict separation of work and review

Workers claim and submit tickets; an independent reviewer on a distinct principal inspects evidence to approve or reject with actionable fix instructions.

Architecture: Central at the core, agents operate locally

Communication is cleanly divided across three layers: a JWT-only Central service backed by SQLite handles state mutations and concurrency arbitrations; MCP connectors expose standardized tools to AI hosts; and the wait bridge multiplexes cross-board push cues without vendor lock-in.

TLS deployment realities: Production fleets run pursers, fullplatts, mi-mcp-prd, and archive boards on a single Central instance behind loopback TLS. However, what the package itself strictly enforces is loopback binding + JWT authentication; other profiles or local setups may run plain HTTP over loopback. Do not claim the package mandates TLS across all installations.

Authentication and admission

  • CENTRAL_AUTH_MODE must be set to jwt; development token transition fallbacks have been removed.
  • The JWT verifier accepts only RS256, loads public keys from CENTRAL_JWKS_PATH, and validates issuer, audience, resource, expiration, subject, and scopes fail-closed.
  • The principal identity is derived solely from cryptographic claims, never from client-declared agent names; board admission requires membership via board_member_add or an invite through board_invite.

Per-board identity derivation

Central deterministically derives each agent_id using this canonical tuple:

agent_id = "AI-" + sha256(
  JSON([board_id, principal_id, agent_name])
)

Consequently, workers using the same agent name under the same principal receive distinct agent_id values on different boards; the fleet dashboard aggregates seat presence by (principal_id, agent_name) rather than agent_id.

board_state applies per-board scrub profiles

Central 0.1.0a25 applies board-specific scrub profiles to board_state_update. An internal board can persist registries containing absolute work_dir paths, while a strict board rejects paths that resemble home directories.

Board generation fencing

Every mutation susceptible to stale writers requires the board’s current generation token. Rejoining returns the latest generation; callers must provide this token with claims, submissions, reviews, and lease renewals rather than assuming prior authorizations remain valid.

Data visibility scope vs. filesystem sandbox

JWT tokens and board memberships govern which boards a principal may observe. In contrast, work_dir entries in the registry serve solely as routing metadata; local filesystem read/write permissions remain governed by the worker host’s OS-level sandbox or container layer.

Personal tier: Same Central, packaged for a single user on a single machine

Profiles and capabilities

pursers-personal setup provisions isolated profiles for boards, Central configurations, credentials, and host configs; doctor validates paths, versions, token identities, CA bundles, and config drift without leaking raw tokens to browsers or stdout.

Full-lifecycle CLI

Running setup without --apply acts as a pure plan-only inspection; failed apply transactions roll back cleanly without leaving orphan profiles, and uninstall strips host integrations while preserving user project data.

Transactional host integration

The Config panel displays redacted diffs prior to application, generates timestamped backups, and signals required host restarts. Release a21 introduced seat imports and granular per-seat or fleet-wide Doctor diagnostics.

Pure-read MCP App facade

The dashboard resource queries board_status, board_snapshot, fleet_snapshot, and the journal event feed using bounded limits without joining or mutating boards; Personal memory_* endpoints remain supported for existing UI consumers.

Security boundary

The Personal tier is designed for a single-user local trust boundary using loopback bindings + JWTs, storing credentials in protected files or secret stores; it is not multi-tenant and does not turn the registry into a filesystem sandbox.

Migration from On Board v4

pursers-personal-import 5.0.0a3 executes a one-way cutover while embedding audit provenance; legacy datastores are never written back to, nor is import intended for bi-directional synchronization.

Cross-Project Fleet: Add a project once, the pool sees the entire system

The registry board hosts the centralized project registry, and a2a_wait(boards="registry") resolves this registry into active boards before listening. Since a16, all seats rely on subscription-first event feeds rather than polling timers.

Added in a22: A blank seat home board indicates a fleet-wide worker serving all active registry boards (boards=registry), with the bridge binding to the registry board (default pursers); a named home board indicates a dedicated seat (boards=home), with the prompt passing boards=["<board>"]. Managed host configs persist this selector via PURSERS_BOARDS / PURSERS_HOME_BOARD.

Project registry contract

Persisted under key project_registry on the registry board as a JSON string matching schema version 1:

{
  "schema_version": 1,
  "projects": {
    "<name>": {
      "board_id": "<board_id>",
      "work_dir": "<absolute_work_dir>",
      "status": "active | paused"
    }
  }
}

Registry admin CLI

tools/wait-bridge/registry_admin.py supports show, add, pause, activate, and remove. All mutations perform strict whole-document validation before writing and execute an immediate read-back verification. Mismatches exit non-zero with diffs; authentication uses ONBOARD_CENTRAL_TOKEN without printing secrets.

python tools/wait-bridge/registry_admin.py add <name>   --board-id <board_id> --work-dir <absolute_work_dir>

Subscription-first + explicit polling

Each accessible board subscribes to both board://<board_id>/journal and seat-specific notification cues via BoardClient.events(). Waking cues trigger a refetch with touch=false. If push notifications fail, the bridge logs the event and degrades only the affected board or call, attempting push reconnection on the next re-arm.

Idle seats generate zero traffic to Central after draining; seats holding active tickets renew only their specific lease within TTL bounds. Long-running work must issue explicit renewals outside of a2a_wait calls.

Failure is actionable data

Multi-board wait responses return a composite new_seq dictionary, every journal event specifies its board_id, and inaccessible boards are recorded under skipped_boards. If the registry is missing or malformed, the system falls back to the home board with a registry_warning rather than fabricating entries.

From registry to Fleet dashboard

The pure-read tool fleet_snapshot discovers active projects from the registry, issues concurrent calls to board_status and bounded board_snapshot across each board without joining or mutating, and aggregates an organization-wide operational view.

Bounded APIs: Bound structures and bytes before controlling prose

Snapshot

board_snapshot bounds projected collections and total UTF-8 JSON byte size, returning total, returned, omitted, and truncated counts alongside high-watermark sequence tokens.

Catchup

board_catchup enforces event count and byte limits, returning has_more flags and updated new_seq cursors; release a21 introduced batching, compaction, and cursor clamping while guaranteeing monotonic progress within deadlines.

Status

board_status delivers a lightweight summary of active and pending board states, replacing the legacy board_get_briefing tool removed in release a21.

Submit

Pursers Client 0.1.0a18 enforces notes length constraints, truncating at line boundaries with explicit truncation metadata to ensure evidence is never silently clipped.

Core principle: Model token limits do not constrain structured transport envelopes. Tools must enforce item, event, and byte limits, requiring callers to paginate using server-provided cursors.

Two dashboard flavors separated by context

Standalone Fleet Dashboard (primary)

The primary operator console hosted on loopback incorporates Home, Work, Agents, Config, Needs Attention, and Release & Operations panels. Release a21 introduced seat imports and seat-level Doctor diagnostics, fleet clone worktree ownership, immutable release planning, Central staging verification, tag publishing, kickstart flows, and restart checklists.

MCP App (inline per-project)

The ui://pursers/dashboard resource provides an inline, pure-read view showing Today, Work, Agents, Fleet, and Activity. It is not an operator console replacement and never receives credentials inside its iframe sandbox.

Added in a22: Panel timer auto-refresh automatically pauses whenever a form holds input focus or contains unsaved modifications, resuming via a fixed “Resume” pill or status bar click. The fleet clone endpoint populates working trees and repairs empty clone directories rather than rejecting them as dirty.

Coordinator: Read, analyze, intake asks, observe dispatch without claiming work

Findings engine

Surfaces deduplicated reports covering stale claims, unverifiable or closed-but-unmerged commits, oversized boards, and integration gaps; board-degraded alerts are reserved strictly for genuine network or call failures.

Structured intake

Deterministic classifiers translate authorized incoming asks into formal tickets through an isolated principal intake, featuring consume-once idempotency tokens and an explicit approval matrix.

Orchestrator digest

board_digest, board_digest_ack, and board watchlists provide non-blocking event buffer reads; orchestrators never issue a2a_wait calls, claim tickets, review submissions, or merge code autonomously.

Dispatcher liveness

Release a21 restricts work offers to verifiable live seats with fair round-robin rotation and persistent offer deadlines across restarts. Release a22 periodically re-surfaces unclaimed broadcast tickets according to PURSERS_BACKLOG_RESURFACE_INTERVAL_S (default 600 s) and re-offers them after the board’s broadcast_reoffer_s, ensuring coordinator identities are never offered work.

Reduced attack surface: agent_nudge has been removed. Autonomous Dispatcher offers serve as the sole targeted waking mechanism.

Core work flow: Wait → Race claim → Understand → Do → Submit → Review

The foundation of safe autonomy is server-side atomic state transitions: exactly one worker wins a claim race. The event journal acts as a wake-up cue rather than a source of truth; workers must always refetch current ticket state before executing tasks.

1

Arm

Call a2a_wait(boards="registry") with latest cursors; on timed_out=true, immediately re-arm using returned new_seq.

2

Claim

Contest offered ticket; losing agents immediately step back to wait rather than duplicate work.

3

Understand

Inspect ticket description, required fields, relevant memories, and any rejection fix instructions.

4

Do

Work strictly within the authorized fleet clone; issue periodic renewals for long tasks.

5

Submit

Report changes, test results, constraints, and verified evidence truthfully without exaggeration.

6

Review

An independent reviewer under a separate principal inspects evidence; approve to close or reject with fix steps.

Team topology & governance: One worker seat maps to one host session and one agent_name per call. Reviewer seats operate under their own distinct principal and must verify reproducible evidence before approving or rejecting. Operators oversee scope and boundaries. Browser verification uses lightweight dedicated headless/lite tools, never unconstrained personal browsers.
a22 — keepalive liveness: Background lease renewal occurs only while the stdio session demonstrates active model liveness within PURSERS_KEEPALIVE_IDLE_LIMIT_S (default three claim TTLs). When idle, renewal pauses with a lease_keepalive_paused notification cue, and the Needs Attention panel flags claims sustained solely by keepalive.

Three seat flavors and work routing

Despite differences in transport mechanisms, all seats authenticate via JWTs, participate in board membership, observe generation tokens, and submit per-call identities. Roles have been declared by seats since a18, and reviewers must belong to a separate principal from submitters.

MCP seat (Codex / Claude Desktop)

Listens via the Wait Bridge using subscription-first multiplexing across boards, refetches ticket state upon cue, and aligns with host timeout profiles to re-arm cleanly prior to client deadlines.

CLI seat (Goose seat-kit)

The seat_new.py generator creates role-safe bin/board.sh wrappers, token launch files, fleet clone workflows, and wait commands driven by registry cursor maps. Release a22 makes --board optional, introduces --registry-board, preserves virtual environment interpreters under --python, and ensures upgrades do not abort on non-fast-forward seat clones.

API seat (worker-runtime)

Headless runtime consuming identical capability, tier, and skill-targeted offers as interactive seats, equipped with bounded wait/submit loops, fleet-owned clone trees, and a strictly reduced tool surface.

Work routing: The Dispatcher issues offers only to active live seats meeting tier, skill, and role permissions. Atomic review leases prevent duplicate inspections, and continuations track prior claim holders and branches across handoffs.

Design rationale

The architectural goal is not creating a single omnipotent agent, but enabling diverse models across vendors to collaborate effectively while operators retain complete control over data, scopes, and accountability.

1. Cross-vendor interoperability is a core feature

  • MCP provides clean boundaries: Any host implementing the standard protocol interacts with identical ticket and memory models without Central needing model-specific logic.
  • Identity bound to individual calls: Multiple concurrent sessions share connectors while Central independently validates their respective agent_name and principal credentials.
  • Server-side atomic arbitration: Even when multiple workers wake concurrently, atomic claim operations ensure exactly one worker is awarded a ticket.

“Let models compete on work quality, not on who overwrites shared state first.”

Core philosophy of Central + ticket leases + independent reviews

2. Local-first architecture minimizes attack surface

  • Central binds exclusively to loopback interfaces in Personal deployments, storing data in user-controlled SQLite databases.
  • Secrets and tokens never appear in configuration diffs, dashboard HTML, iframe messages, tool outputs, or logs; documentation examples use placeholders such as <token>.
  • Dashboards operate in pure-read mode; file modification rights remain strictly governed by the OS-level file-editing layer within /PATH/TO/project rather than the board.

3. Cloud-ready without redesign

  • JWTs partition issuers, audiences, scopes, and principals from day one, facilitating straightforward integration with enterprise identity providers.
  • Journal cursors, bounded snapshots, and idempotent event streams gracefully accommodate network interruptions and client reconnects.
  • Cryptographic artifact locks and pinned build environments ensure reproducible verification across external cloud runners.

Operational realities and guardrails

While this briefing articulates the v5 architecture, conceptual capabilities must not be mistaken for security assurances beyond what the codebase enforces.

The registry is routing metadata, not a filesystem sandbox

The project_registry maps board identifiers to local work_dir paths; it does not grant or restrict filesystem read/write permissions. Filesystem safety must be enforced by container runtimes or host-level sandboxes, while board access is governed by membership.

Push events are cues, not authoritative payloads

When subscriptions/listen wakes a bridge, the client must refetch state using touch=false before taking action. If push notifications fail, the bridge gracefully falls back to polling for that board and retries push subscriptions on the next re-arm.

Leases expire

The wait bridge only renews leases for tickets actively held by the seat during an ongoing a2a_wait call; idle seats emit no keepalive signals. Long operations must call lease_renew directly to prevent background reapers from returning the ticket to the open backlog.

Review requires independent principals

Differing agent names may belong to the same underlying principal. Strict review governance verifies that the submitter and reviewer principals differ, and reviewers must independently inspect test and execution evidence before approval.

60-second executive summary

01

Central is the impartial umpire

SQLite persists ticket state and journal logs; JWT-only auth and memberships control board access, while atomic claims eliminate collision races.

02

The registry enables fleet coordination

The wait bridge discovers active boards from the registry, maintaining isolated subscriptions and cursors; timer polling serves strictly as an intentional fallback.

03

Work is complete only when verified

Worker seats submit changes; independent reviewer seats on distinct principals approve or reject; fleet dashboards provide visibility, and workers re-arm upon closure.
