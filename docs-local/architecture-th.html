ภาพจำสั้น ๆ ก่อน

Pursers ไม่ใช่ที่เก็บไฟล์โปรเจกต์ และไม่ใช่ AI ตัวใหม่ แต่เป็น “หอบังคับการงาน” ที่ทำให้หลาย agent เห็นคิวเดียวกัน แย่งงานโดยไม่ทำซ้ำ และมีหลักฐานว่าใครทำ ใครตรวจ และจบเมื่อไร

N boards

หนึ่ง fleet หลายโปรเจกต์

แต่ละโปรเจกต์มี board และ cursor ของตัวเอง แต่ registry ทำให้ wait-bridge เฝ้าหลาย board ผ่าน transport เดียวได้

N seats

หนึ่ง session ต่อหนึ่ง worker seat

Codex, Claude หรือ host อื่นส่ง agent_name ต่อ call; Central derive identity แยกต่อ board โดยไม่ทับ state กัน

2 roles

ทำงานกับตรวจงานแยกกัน

worker claim และ submit; reviewer อีก principal ตรวจแล้ว approve หรือ reject พร้อมคำสั่งแก้ จึงย้อนดูความรับผิดชอบได้

สถาปัตยกรรม: Central อยู่กลาง แต่ agent ยังทำงานในเครื่องตัวเอง

การสื่อสารแบ่งเป็นสามชั้นชัดเจน: Central แบบ JWT-only เก็บสถานะและตัดสินการแข่งขัน, connector แปลงเครื่องมือ MCP ให้ host เรียกได้, ส่วน wait-bridge รับหน้าที่รอ cue ข้ามหลาย board โดยไม่ผูก Central เข้ากับยี่ห้อใดยี่ห้อหนึ่ง

เรื่อง TLS ที่ควรเล่าให้ตรง: fleet ที่ใช้งานจริงวาง pursers, fullplatts, mi-mcp-prd และบอร์ด archive บน Central เดียวหลัง loopback TLS แต่สิ่งที่ตัว package code บังคับโดยตรงคือ loopback + JWT-only; profile หรือ deployment อื่นอาจใช้ HTTP loopback ได้ จึงไม่ควรอ้างว่าแพ็กเกจ pin TLS ให้ทุก installation

Authentication และ admission

  • CENTRAL_AUTH_MODE ต้องเป็น jwt; dev-token transition fallback ถูกถอดออกแล้ว
  • JWT verifier รับเฉพาะ RS256, โหลด key จาก CENTRAL_JWKS_PATH และตรวจ issuer, audience, resource, expiry, subject และ scope แบบ fail-closed
  • principal มาจาก signed claims ไม่ใช่ชื่อ agent; การเข้าแต่ละ board ต้องเป็น member ผ่าน board_member_add หรือ invite ที่ออกด้วย board_invite

Identity แยกทุก board

Central สร้าง agent_id แบบ deterministic จาก tuple นี้:

agent_id = "AI-" + sha256(
  JSON([board_id, principal_id, agent_name])
)

ดังนั้น worker ชื่อเดียวกันภายใต้ principal เดียวกันจะยังได้ agent_id คนละค่าเมื่ออยู่คนละ board; dashboard จึงต้องรวม pool ด้วย (principal_id, agent_name) ไม่ใช่ด้วย agent_id

board_state ใช้ scrub profile ของ board

Central 0.1.0a23 ใช้ scrub profile ของบอร์ดกับ board_state_update บอร์ด internal จึงเก็บ registry ที่มี absolute work_dir ได้ ขณะที่บอร์ด strict ยังปฏิเสธ path ลักษณะ home directory

ขอบเขตข้อมูลกับขอบเขตไฟล์

JWT และ membership ตัดสินว่า principal เห็น board ใด ส่วน work_dir ใน registry เป็นข้อมูล routing เท่านั้น สิทธิ์อ่าน/เขียนไฟล์ยังต้องถูกบังคับโดย sandbox หรือ file-editing layer ของ worker แยกต่างหาก

Cross-Project Fleet: เพิ่มโปรเจกต์หนึ่งครั้ง แล้ว pool เห็นทั้งระบบ

Home board เก็บ project registry กลาง แล้ว a2a_wait(boards="registry") แปลง registry เป็นรายการ board ที่ active ก่อนเริ่มรอ ใน a16 ทุก seat ใช้ subscription เป็นเส้นทางหลักแทน timer poll

Project registry contract

ค่าอยู่ที่ key project_registry บน home board และเก็บเป็น JSON string ตาม schema ที่รับเฉพาะ field เหล่านี้:

{
  "schema_version": 1,
  "projects": {
    "<name>": {
      "board_id": "<board_id>",
      "work_dir": "<absolute_work_dir>",
      "status": "active | paused"
    }
  }
}

Registry admin CLI

tools/wait-bridge/registry_admin.py รองรับ show, add, pause, activate และ remove ทุก mutation ตรวจ schema ทั้ง document ก่อนเขียน แล้วอ่านกลับเทียบค่า; mismatch จบ non-zero พร้อม diff และ token มาจาก ONBOARD_CENTRAL_TOKEN โดยไม่พิมพ์ออกมา

python tools/wait-bridge/registry_admin.py add <name> \
  --board-id <board_id> --work-dir <absolute_work_dir>

Subscription-first + poll แบบ explicit

แต่ละ accessible board subscribe ทั้ง board://<board_id>/journal และ per-seat cue ผ่าน BoardClient.events() Cue เป็นเพียงสัญญาณให้ refetch แบบ touch=false เท่านั้น หาก subscription ใดล้ม จะ log ชัดและลดระดับเฉพาะบอร์ด/call นั้น ก่อนลอง push ใหม่ในการ re-arm ถัดไป

seat ว่างไม่เรียก Central หลัง drain ก่อน subscribe; seat ที่ถือ ticket ต่ออายุเฉพาะ lease ที่ถืออยู่ตาม TTL งานที่กำลังทำต้อง renew เองนอกช่วง a2a_wait

Failure เป็นข้อมูล ไม่ใช่การเดา

ผล multi-board ส่ง new_seq เป็น map, event ทุกตัวมี board_id และ board ที่เข้าไม่ได้อยู่ใน skipped_boards หาก registry หายหรือ malformed ระบบกลับมาเฝ้า home board พร้อม registry_warning โดยไม่สร้างรายการ project ขึ้นเอง

จาก registry สู่ Fleet dashboard

เครื่องมือ pure-read fleet_snapshot โหลดเฉพาะ project ที่ active แล้วเรียก board_status และ bounded board_snapshot ของแต่ละ board โดยไม่ join identity ใหม่ ก่อน aggregate เป็นมุมมองระดับองค์กร

Flow หลัก: รอ → แย่ง claim → ทำ → ส่ง → ตรวจ

หัวใจคือ server เป็นผู้เปลี่ยนสถานะ ticket แบบ atomic จึงมีผู้ชนะ claim เพียงคนเดียว ส่วน journal เป็น cue ให้ตื่น ไม่ใช่สำเนาความจริง Worker ต้องอ่าน ticket ล่าสุดก่อนลงมือเสมอ

1

Arm

เรียก a2a_wait(boards="registry") ด้วย cursor map ล่าสุด; timed_out=true ให้ re-arm ทันทีด้วย new_seq

2

Claim

ถ้าแพ้การแข่งขันให้กลับไป wait ห้ามฝืนทำ ticket เดียวกัน

3

Understand

อ่าน ticket, required fields, memory และคำสั่งแก้ล่าสุด

4

Do

ทำใน scope ที่อนุญาต งานยาวต้องต่ออายุ lease เอง

5

Submit

บอกสิ่งที่ทำ สิ่งที่ทดสอบ และข้อจำกัดตามจริง

6

Review

reviewer seat คนละ principal ตรวจ; approve → close, reject → แก้และ submit ใหม่

รูปแบบการจัดทีม: worker seat หนึ่งที่นั่งคือหนึ่ง Codex session และหนึ่ง agent_name ต่อ call; reviewer seat แยกอยู่ภายใต้ principal ของตัวเองและต้องตรวจ evidence ก่อน approve/reject มนุษย์เป็นผู้กำกับ scope และผลลัพธ์ สำหรับงานตรวจผ่าน browser ใช้ ego lite เท่านั้น ไม่ใช้ Chrome

ทำไมออกแบบแบบนี้

โจทย์ไม่ใช่ทำ agent ที่เก่งที่สุดหนึ่งตัว แต่ทำให้ agent หลายค่ายทำงานร่วมกันได้โดยทีมยังควบคุมข้อมูล สิทธิ์ และความรับผิดชอบ

1. Cross-vendor คือจุดขาย ไม่ใช่ของแถม

  • MCP เป็นเส้นแบ่งที่ชัด: host ใดทำตามสัญญาเดียวกันก็ใช้ ticket และ memory ชุดเดียวกันได้ โดย Central ไม่ต้องรู้ว่าโมเดลข้างหลังคืออะไร
  • identity อยู่ที่ call: หลาย session ใช้ connector เดียวกันได้ แต่ทุก action ยังมี agent_name และ principal กำกับ
  • การแข่งขันจบที่ server: ต่อให้ worker หลายตัวตื่นพร้อมกัน การ claim แบบ atomic ทำให้มีผู้รับงานเพียงตัวเดียว

“ให้โมเดลแข่งกันที่คุณภาพงาน ไม่ใช่แข่งกันว่าใครเขียนทับสถานะก่อน”

แนวคิดของ Central + ticket lease + independent review

2. Local-first ลดพื้นที่เสี่ยง

  • Central bind เฉพาะ loopback ใน Personal deployment และเก็บ SQLite ใน profile ที่เจ้าของควบคุม
  • token ไม่ควรเข้า config ที่เปิดเผย, dashboard HTML, iframe message, tool result หรือ log; ตัวอย่างใช้ <token> เท่านั้น
  • dashboard อ่านภาพรวม ส่วนสิทธิ์แก้ไฟล์ยังเป็นของ file-editing layer ใน <work_dir> ไม่ใช่สิทธิ์ที่ board แจก

3. พร้อมขยายขึ้น cloud โดยไม่รื้อโมเดล

  • JWT แยก issuer, audience, scope และ principal ตั้งแต่ต้น จึงต่อยอด identity provider และ remote boundary ได้
  • journal cursor, bounded snapshot และ idempotent event ทำให้รองรับการเชื่อมต่อที่หลุดแล้วกลับมาใหม่
  • artifact lock และ pinned toolchain ช่วยให้ deploy ที่อื่นแล้วยังตรวจ provenance ได้

ขอบเขตจริงที่ต้องพูดให้ครบ

ภาพรวมนี้อธิบายทิศทาง v5 แต่ไม่ควรแปลงแนวคิดเป็นคำรับรองด้าน security หรือความพร้อม production เกินกว่าที่ code ปัจจุบันทำได้

Registry คือ routing ไม่ใช่ security fence

project_registry บอกว่า board ใด map ไป work_dir ใด แต่ไม่ได้ให้สิทธิ์อ่านไฟล์; ต้องจำกัดที่ file-editing MCP หรือ sandbox และใช้ membership แยกสำหรับสิทธิ์บน board

Push เป็น cue ไม่ใช่ payload ที่เชื่อทันที

เมื่อ subscriptions/listen ปลุก bridge ระบบจะ refetch journal/ticket แบบ touch=false แล้วกรองใหม่; ถ้า push ล้มเหลวจะ fallback เฉพาะ board/call นั้นและ retry push เมื่อ re-arm

Lease มีอายุ

wait-bridge renew เฉพาะ lease ที่ seat ถือและเฉพาะตอนอยู่ใน a2a_wait; seat ว่างไม่มี heartbeat ไป Central งานที่ใช้เวลานานต้องเรียก lease_renew เอง ไม่เช่นนั้น reaper อาจคืนงานสู่คิว

Review ต้องแยกตัวตนจริง

ชื่อ agent ต่างกันยังอาจถือ principal เดียวกันได้ นโยบาย strict จึงตรวจ principal ของผู้ submit กับ reviewer ไม่ใช่เทียบเพียงชื่อ และ reviewer ต้องตรวจ evidence จริงก่อนตัดสิน

สรุปเอาไปเล่าใน 60 วินาที

Central คือกรรมการกลาง

SQLite เก็บสถานะและ journal; JWT-only + membership กำหนดผู้เข้า board และ claim แบบ atomic กันงานซ้ำ

02

Registry ทำให้เกิด fleet

wait-bridge โหลด active boards จาก home registry แล้วรักษา cursor และ subscription แยกต่อ board; timer poll ใช้เฉพาะ fallback ที่ตั้งใจ

03

งานจบเมื่อคนอื่นตรวจ

worker seat submit, reviewer seat คนละ principal approve หรือ reject; Fleet tab แสดงภาพรวม และ worker re-arm หลังปิดงาน
