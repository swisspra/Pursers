# Resident workflow cohort delivery adapter

`tools/board-butler/workflow_delivery.py` is a small adapter around the existing `BatchDeliveryRuntime`, `BatchLedger`, and `VerifiedGitConnectorAdapter`. It is deliberately not a scheduler, source validator, Git engine, QA-ticket creator, or PR implementation. The resident workflow/native owner must supply an activated, normalized policy and actual member records backed by independent review and validation.

## Contract

```python
prepared = await prepare_workflow_delivery(
    runtime, delivery_policy, workflow_policy, members
)
result = await publish_workflow_delivery(
    runtime, delivery_policy, workflow_policy, qa_ticket, prepared
)
```

`workflow_policy` is the exact sealed v1 normalized project policy (`board_id`, `project_name`, `cohort_id`, ordered `member_ticket_ids`, prerequisite `nodes`, `final_validation`, `activation_id`, and canonical `policy_revision`). For normal preparation, `final_validation.combined_revision` may be an explicit `null` pending-head marker; otherwise it remains a required full SHA and is strictly checked against the actual runtime head. `members` has exactly one validated member per declared ID and includes truthful nonempty `blockers` and `baseline_failures`, plus `origin` when available. Independent evidence must attest the same source SHA; origin is retained as audit context and must agree with evidence when supplied. Empty `issue_ids` are valid for coordinator-origin members.

A successful prepare returns `state="prepared"`, the existing durable `batch_key`, actual cumulative `combined_revision`, complete ticket-to-approved-SHA `member_manifest`, source refs, member approval-evidence digests, manifest digest, cohort ID, sealed workflow-policy SHA-256, final-validation-policy digest bound to the actual head, and delivery-policy revision. The wrapper calls the runtime's existing collection once for each member (including real integration merges), derives the cumulative SHA from the runtime ledger, and does not request release. It fails closed on partial, extra, stale, changed, split, or unsealed membership; unavailable refs and other blocked runtime outcomes remain explicit blocked outcomes. Existing remote-operation reservations and unknown-outcome reconciliation are preserved.

Final QA must be closed with a current independent approve verdict, distinct submitter/reviewer principals, and a verdict tied chronologically to its latest actual Central submission. Central persists submission `commit_hash`, `notes`, submitter identity, and timestamp, plus review `submission_commit`, `review_notes`, reviewer identity, verdict, status, and timestamp; it does not persist typed `validated_sha` or `workflow_delivery` verdict fields. The exported `workflow_delivery_attestation(prepared)` helper returns the canonical line `workflow_delivery_sha256: <lowercase-sha256>` over the full prepared identity (sorted keys, compact UTF-8 JSON). That exact marker must occur once in actual Central submission notes and once in actual independent `review_notes`; each is separately checked against the prepared identity. The actual submitted `commit_hash` and review `submission_commit` must equal the prepared combined head. Fabricated ticket/verdict fields alone cannot authorize publication. The native controller separately verifies its immutable QA packet equals the prepared result; a mutable ticket field is not reviewer attestation. Keep the full readable QA packet in the task body rather than echoing it into Central's 5,000-character notes. A pending input is only a preparation marker: it cannot authorize publication. Missing, duplicate, conflicting, malformed or wrong markers, stale/current-review mismatch, same-principal QA, or head/policy/member/ref drift denies release. The adapter re-reads the runtime integration ref and each approved member source ref, then rechecks policy, durable batch head, cohort/member/ref identity and Central-history attestation before calling the runtime's existing release once with the sealed cohort request. It does not waive human holds, infer validation success, or retry unknown customer operations itself; the runtime owns its existing ledger, connector, busy-slot, and reconciliation behavior. Existing `per_ticket_pr` remains an explicit legacy outcome.

For `batch_pr`, mapped/base and customer PR target may be the exact same branch: the base is a read input and the target is a PR destination. The integration branch and frozen snapshot namespace remain owned, distinct references. A batch PR may not alias its owned integration ref or use case-only aliases. No customer environment ref is written, force-pushed, or finally merged by this adapter. `branch_only` publishes only the configured owned snapshot branch.

Managed SourceIntake entries remain in-flight while native QA is pending, then settle only after the delivery ledger and current immutable snapshot/PR ref independently confirm the exact prepared cohort. A correlated active PR is recorded with its PR identity; branch-only delivery is recorded as a published branch without inventing a PR. Missing or ambiguous replay receipts, changed refs, mismatched cohort/member/head bindings, and unknown remote outcomes leave entries protected in-flight. Settlement is durable and idempotent, so a restart can recover confirmed `batch_pr` replays that omit an ephemeral `pr_id` from their response.

Focused disposable-Git tests live in `tools/board-butler/tests/test_workflow_delivery.py`; parser compatibility regressions are in the existing client delivery-policy tests and `test_batch_delivery_runtime.py`. Tests use a temporary bare origin and fake connector, without paid models or customer actions.
