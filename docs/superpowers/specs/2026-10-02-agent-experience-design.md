# Pursers agent and operator experience

Status: approved direction under delegated operator authority; implementation pending fleet tickets.
Baseline inspected: Pursers `1b0c2216fa4cf90b3f5347a372653c079d80d356`; website `71eb3a8426f93d08b5c3689d15f3c45c7524693b`.

## Outcome

Pursers is the OS for your agent fleet. MCP provides connectivity; Pursers provides durable work, identities, authorization, coordination, independent review, delivery, and operational visibility.

Make everyday work understandable without reading the whole board or learning every tool. A new person should connect a supported client, choose an authorized project and role, understand the next action, and follow a ticket through delivery. An agent should retrieve only the instructions and evidence needed for its current task.

The coordinator owns this design and board dispatch. Existing Mac workers implement it; separate fleet reviewers verify it. No new model agents, service restarts, deployments, publishing, or version bumps are authorized by these implementation tickets. These documents describe proposed behavior, not released capability.

## Evidence and decisions

| Area | Already present | Actual gap and decision |
| --- | --- | --- |
| Ticket reads | `summary/work/full`, bounded snapshots, archive index, event catch-up cursors | `ticket_list` has a limit but no continuation. Add application-level pagination and explicit history navigation; keep compact projections. |
| Progress | Lease-bound `ticket_progress_update`, ranges/confidence/evidence/freshness; dashboard support; feature flag | Extend durable lifecycle visibility to review and delivery. Use MCP progress only for an individual long tool call. |
| Context | SDK Context already injected in Central; SDK 2.2.0 pinned | No migration or standalone Context rewrite. Context is request infrastructure, not an automatic token-saving mechanism. |
| Discovery | Relay prompts `board/create/watch/evidence/answer/setup`; wait bridge digest resource | Reuse these and add an authorized, lazy resource/help catalog with useful fallbacks. |
| Skills | Extensive guides and seat tooling | Publish a small portable skill bundle and role-based onboarding using canonical docs. |
| Agent names | Persistent `agent_name`, principal and agent IDs | Add editable display names without changing identity, roles, leases, or credentials. |
| Public site | React/Vite landing page and Cloudflare/Hono health API | Adopt Astro for content and multiple routes. Keep private fleet dashboard independent. |

Rejected: a full SDK migration; replacing all tools with resources; pagination of a small tool catalog for its own sake; making all progress a percentage; a new global identity provider; rewriting the fleet dashboard in Astro; loading every skill into every model prompt; promising token savings without measurements.

## Shared invariants

- Existing permissions remain authoritative on every page/read/write/subscription. Client headers, cursors, display names, resources, prompts, and skills never grant permissions.
- A compact response states omissions and how to retrieve more. It must not imply that a bounded page is the entire board.
- Preserve original ticket IDs, source membership, independent-review rules, lease ownership, submission evidence, and delivery policy. UI state must not mutate workflow implicitly.
- Private board data stays private. Public website/examples use synthetic data and relative paths, never production screenshots, credentials, hostnames, company identifiers, or internal handoffs.
- Existing clients keep working. Feature discovery and explicit unsupported states replace guessing. No broad automatic configuration changes.
- New records and cursors use schema versions. Writes use existing authorization and concurrency mechanisms. New fields are additive; reads tolerate older records. Document rollback and old-client behavior.
- Every stream updates its user guide, configuration reference where applicable, and an unreleased changelog entry. Generated reference/artifact changes are requested for the integration operator, not manually regenerated by workers.

## 1. Lean reads and pagination

### User journey

Work lists initially show a compact first page and exact filter scope. Users can request the next page without reloading full descriptions, annotations, or dispatch history. A ticket opens with its actionable summary; evidence/history is loaded explicitly. Agents use the same contract and can request `work` or `full` when their task requires it.

### Contract

- Extend `ticket_list` with optional opaque `cursor` and additive `next_cursor`, `has_more`, `returned_count`, `read_consistency`, and a watermark. Keep current filters and legacy response keys. An omitted cursor starts a new traversal; only `next_cursor=null` means no further page in that traversal.
- Use keyset ordering with the current priority ordering plus immutable ticket ID as tie-breaker. Bind a versioned, integrity-protected cursor to board, effective principal, canonical filters, ordering, view, and archive mode. Check current authorization on every request. Invalid, mismatched, or unsupported cursors return actionable errors, not an empty successful page.
- Explicitly advertise live-read consistency: under concurrent priority/status/archive changes, membership/order may change. Consumers deduplicate by ticket ID and refresh after relevant events. Do not promise an atomic snapshot or use these pages alone as proof that no work remains. A quiescent scan must enumerate every matching ticket exactly once.
- Keep `board_snapshot` plus journal splice/catch-up semantics unchanged. Its bounded projection is not a complete listing. Authoritative scheduling and negative conclusions continue to use existing exhaustive/consistency-aware paths.
- Keep default limit and maximum compatible initially. Bound serialized response bytes as well as row count. For an unusually large single item, return a retrievable summary with explicit omitted sections rather than silently dropping it. Do not destructively truncate stored ticket text.
- Page retained ticket history separately, using stable event/annotation identifiers and chronological order. Expose retention boundaries and unavailable/archived sections honestly. Do not reconstruct evicted history as if it were stored evidence.
- Use the compact archive index for filtering; hydrate bodies only for returned items that need them. Prefer summary reads in list consumers; preserve explicit full detail access and legacy API defaults until documented migration.
- SDK list pagination is a different layer. Do not alter `tools/list` unless measured catalog size justifies it and host interoperability tests cover complete discovery.

### Acceptance

Test hot/archive boundaries, equal priorities, every filter, invalid cursor, permission changes, empty/end pages, byte bounds, oversized detail, and concurrent updates. Prove complete quiescent traversal without duplicate/lost IDs. Benchmark serialized bytes and archive hydration for 100 and 1,000 synthetic tickets with long histories; compare current behavior with the same fixtures. Report model tokens only if a named tokenizer or provider measurement is available. No invented savings percentages.

## 2. Durable lifecycle and truthful progress

### Presentation

Show a durable stage and its latest evidence: intake/planning, queued, claimed/work, validation, independent review, integration, delivery, completed. These are a presentation projection of real events, not a new state machine that bypasses existing transitions. Some projects skip stages or stop at a PR; show not-applicable or the configured completion boundary.

Show actor, attempt, last meaningful update, freshness, blocking reason, and next expected actor/action. Distinguish waiting, running, blocked, retrying, failed, canceled, stale, and unknown. Independent review rejection creates a new work attempt while retaining earlier evidence. Submission, approval, PR creation, merge, and release are different facts; a ticket reaching one must not be displayed as reaching all.

### Contract

- Add a versioned additive `activity` projection to ticket reads/events: `stage`, `state`, `attempt_id`, `actor_id`, `updated_at`, `freshness`, `evidence_refs`, `next_action`, and optional `estimate`. Final vocabulary/types are documented before adapters are written.
- Derive known transitions from authoritative Central and delivery events. Explicit agent updates are accepted only from the currently authorized role/lease for that stage. Keep existing work progress validation and its feature flag compatible.
- Estimates are optional ranges with evidence/confidence. Never derive overall percent from stage number, elapsed time, heartbeat count, or a model's unsupported guess. Unknown total means no percent or ETA. Test execution counts can be shown only when the runner actually supplies a known total.
- Progress updates never renew leases or confer authority. Heartbeats may establish liveness but cannot reset meaningful-progress freshness. Repeated semantic updates are coalesced; use existing bounded journal/retention infrastructure rather than a second unbounded event store.
- Review, integration, and writeback adapters report their real outcomes, including unsupported/not-started; no LLM call merely to repaint a status badge. Read-only projection has no side effects.
- Dashboard reload/reconnect loads durable state then catches up from its watermark, deduplicating events. Do not lose progress across process restarts or rely on browser memory. Prefer existing event subscriptions; bounded compatibility polling only if the host lacks them.
- Optional SDK `ctx.report_progress` serves a long individual tool invocation when the caller requests notifications. Values increase within that invocation; unknown totals are omitted. These notifications supplement durable records, never replace them. Handle callbacks arriving after the tool result.

### Acceptance

Happy flow and rejection/retry, lease expiry, worker crash, stale/no estimates, reviewer ownership, integration conflict, delivery policy differences, and reconnection. Unauthorized updates fail without changing state. Verify a dashboard viewer can tell what is happening and why it is waiting without reading logs. Test both feature-flag settings and older stored records. No fake activity on idle boards.

## 3. Resources, prompts, and small role context

### Discovery contract

Introduce a small versioned capability/help index with role and host support. Proposed stable public URIs: `pursers://help/index`, `pursers://help/roles/{role}`, `pursers://help/workflows/{workflow}`. Board-scoped resources use `pursers://boards/{board_id}/...` with the same authorization as equivalent tools. Retain the existing `board://{board_id}/digest` compatibility resource where supported.

The index lists titles, purpose, URI, version, and applicability, not every body. Board digest and ticket summaries link to detail resources/tools rather than repeating histories. Keep static procedural help separate from dynamic board content and label both. Resource content is read on demand; clients without resource or prompt support get equivalent short tool help and canonical documentation links.

Reuse and improve existing `board/create/watch/evidence/answer/setup` prompts. Prompts prepare a workflow; they do not create/claim/approve/publish without the caller's authorized action. State role prerequisites and safe next steps. Avoid coupling every prompt to one IDE. SDK Context stays server-side and out of model-visible tool arguments; do not turn caller-supplied headers into authority.

Support both Central's current protocol and the relay's legacy host path, including Zed. Verify actual resource reads, prompt discovery/rendering, authorization failures, subscription negotiation, and changed-resource behavior. A URI used by a notification is not proof that `resources/read` works. A missing engine returns an explicit unavailable result, not a misleading empty healthy board.

No hidden chain-of-thought, JWTs, host paths, raw process environment, private memories, or complete boards in the catalog. Treat embedded issue/repository text as untrusted data. Cache static help by content version; never reuse private cached content across principals or stale authorization. Measure initial discovery and a representative task's payload sizes.

## 4. Portable skills and onboarding

Proposed bundle: `pursers-start`, `pursers-work`, `pursers-review`, `pursers-operate`. Keep triggers narrow and descriptions useful. Put essential non-obvious rules in SKILL.md; role-specific detail belongs in progressive reference files or canonical docs. Cover coordinator, Butler, and release-operator responsibilities under operate references, without making all agents load them.

Skills teach discovery, choosing the right board/project, minimal reads, lease-aware work, independent review, evidence, delivery boundaries, and recovery. They do not issue credentials, expand roles, auto-merge, auto-publish, or override human instructions. Provide explicit fallback when a resource/tool/version is unavailable. Avoid embedding one installation's private operator policies as universal product rules.

Build a short onboarding path: identify host and role; connect an existing endpoint using supported auth; verify access without printing secrets; select an authorized project; inspect capabilities; run a harmless read; explain the next allowed action. Zed is the primary GUI journey; Codex and Goose are CLI journeys. Roles without work capability should not see a claim-work instruction as their default next action.

Use canonical existing guides instead of duplicating whole manuals. Ship a versioned manifest for the skill bundle and a safe documented per-host installation/check/removal path. Preview filesystem/config changes, preserve existing user files, require explicit replacement of conflicts, support idempotent upgrades, and never auto-edit global AGENTS files or install into every host. Discover actual host support before promising native integration. The website links to released packages/docs and marks unreleased features accordingly.

Acceptance includes independent-reviewer walkthroughs: fresh user without credentials, wrong board, unsupported resources, existing skill collision, restart/resume with a lease, blocked test baseline, review conflict, and release outside authority. Validate metadata/links and package inclusion. Document what was exercised, not merely that the text looks good.

## 5. Persistent display names

Keep `agent_name` immutable as the operational identity; it contributes to `agent_id`. Add an optional **board-scoped display name** on the existing exact agent identity. It survives normal process restarts and token refresh for the same principal/name. A different principal or agent_name is a different identity; do not silently merge histories. Cross-board alias synchronization is deferred, not implied.

Self-service update requires ownership of that identity; administrative edits require existing board administration authority. Use a narrow validated update API with compare-and-set revision, audit old/new values, and reset-to-default. No role, capability, key, lease, or principal changes in this endpoint. A central profile helper owns persistence; UI must not store the only copy.

Allow duplicate human labels with visible disambiguation by operational name/board. Selection, assignment, permissions, deduplication, and URLs always use stable IDs. Bound labels with a documented UI/storage reason; normalize surrounding whitespace, reject control/bidirectional override characters, and render text safely. Preserve normal international names. Historical events retain their original actor ID/name; optionally show the current alias alongside the original, never rewrite audit evidence.

Show display name with operational name available in team cards, actor selectors, ticket activity, and details. Empty/older records fall back to agent_name. Accessible edit/save/cancel/error states, keyboard operation, and honest permission feedback are required.

## 6. Public website and information architecture

Use Astro for content pages and small React islands only where interaction warrants them. Preserve the existing visual identity (warm neutral surfaces, restrained teal, readable display typography). The private operational dashboard remains its own application.

Routes: `/` (positioning and fit), `/how-it-works/` (lifecycle and architecture), `/get-started/` (host/role choices), `/docs/` (task and role navigation), `/integrations/` (verified support matrix), `/releases/` (released changes). Deeper guides may use a local content collection or curated canonical links; define a single source for each document. Provide useful search/navigation, breadcrumbs where needed, copyable verified commands, and clear current/planned support labels. Do not copy all repository docs into a second unmanaged source tree.

Happy-flow narrative: connect -> register/choose project -> intake -> scoped/grouped ticket -> parallel work -> independent review -> policy-controlled integration -> delivery. Explain that completion depends on configured delivery mode, including one consolidated PR. Use synthetic examples, not private team briefing material. Do not imply every project supports every automation or that all skills/resources in this plan are already released.

Preserve Hono `/api/*` and health behavior, security/cache headers, Cloudflare bindings, custom domains, and asset handling. Replace blanket SPA fallback with real route/404 behavior. Preserve old anchor destinations through compatible IDs or redirects. Validate direct deep links, trailing slash policy, canonical URLs, sitemap, accessible document structure, and no broken released-version links. Verify the current Astro/Cloudflare integration against official docs before choosing compatible versions.

UI principles: clear primary path, no marketing-only pseudo controls; purposeful short feedback animation only; no animation on repeated status updates; reduced-motion support; hover gated to capable pointers; keyboard-visible focus; useful no-JavaScript content. Responsive and light/dark contrast checks, page weight comparison, and browser evidence at mobile/desktop sizes are required. Build and deployment dry-run only; operator owns publishing.

## Execution, ownership, and integration

| Stream | Primary ownership | Shared seams / dependencies |
| --- | --- | --- |
| 01 Reads | New read/cursor helper, Central list/detail, client list adapters | Coordinate thin central.py edits; keep snapshot/wait semantics stable. |
| 02 Progress | New activity projection helper, Central events, runners, dashboard Work | Coordinate central.py and relay registration with 01/03/05; owns activity schema. |
| 03 Discovery | Resource/help catalog, relay prompts, wait-bridge compatibility | Owns URI/capability manifest; supplies optional discovery to 04. |
| 04 Skills | Skill bundle, existing guides, onboarding/install surfaces | Can begin with released tools and fallback links; reconcile catalog with 03 before final approval. |
| 05 Names | Agent profile helper, identity update API, dashboard Team/actor rendering | Preserve identity invariants; coordinate shared actor UI with 02. |
| 06 Website | Separate website repository | Can build against released capabilities; final integration checks claims against 01-05. |
| 07 Acceptance | Integration report and cross-surface consistency | Parked until 01-06 reviewed; operator owns generated artifacts and release actions. |

All six implementation streams may start independently. Before editing a shared file, annotate the ticket with the intended seam and inspect other active work. Keep new logic in focused modules and central registration changes small. Publish exact branch/commit and test evidence; do not opportunistically refactor another stream. If a prerequisite is unavailable, use documented compatibility fallback or mark the dependency; do not invent an implementation or hold a lease without progress.

Each worker starts from current main in its routed repository, reads this design from the planning branch, and creates its own work branch. Planning documents are not a product feature branch dependency. Independent reviewers verify acceptance against implementation and supported old behavior. Shared commits are reconciled at integration; no worker merges main, deploys, restarts seats, or cuts a release.

Rollout sequence after review: additive backend APIs -> compatible relay/runner clients -> dashboard and onboarding -> public released-feature claims. Keep existing progress flag behavior until an operator enables supported adapters. Rollback restores prior client/UI while additive records remain readable; no destructive migrations in this program. Release numbers, generated manifests, full strict CI, and deployment are a separate operator decision.
