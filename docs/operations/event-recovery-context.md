# Event runner project and workspace context

The native event runner starts one worker or reviewer for a current authorized Central event. Goose/Codex must keep its process CWD at the seat identity directory so `AGENTS.md`, MCP identity, and seat policy remain correct; code work is directed separately by the runner's verified project/workspace context.

## Routing, authorization, and preflight

Before paid model launch, the runner reads the current full ticket from the event's exact board and uses the active project registry loaded at bootstrap. Source work is recognized generically from source contract fields (`base_and_head_sha`), conventional source submission fields/metadata, code tags, or an exact registered ticket-bound Git worktree; it does not require a `production-code` tag or a `branch_and_commit` field. A source ticket must have a target that resolves unambiguously through `pursers_client.project_registry.resolve_registry_target` to an active project on that board. The registry's protected `fleet_clone_dir` must be under the configured repository root and its Git top-level and credential-free HTTPS `origin` must match the registered `repository_url`. Event/ticket payload hints do not override Central's current ticket. Contextless non-source tasks without a target remain runnable without an inferred project.

Workspace provisioning (mkdir, Git worktree creation, and ticket branch creation) is a protected common-directory side effect. Do not perform it while validating a cue. First verify the exact live lease for this agent and principal, or verify an authorized current offer and successfully claim/refetch Central ownership. Only then resolve or provision the ticket worktree. Stale/foreign events must leave directories, Git worktrees, and branches unchanged. If claim admission fails, proceed only if a fresh Central read verifies this exact identity now owns a live lease; otherwise skip or surface the original persistent authorization error.

A missing, ambiguous, mismatched, or unsafe source route/workspace fails closed before model launch with a typed context error. For an already-owned lease or a successfully acquired authorized offer, the runner records an actionable coordination question and requests a Central hold, verifies that Central reports `needs_human`, and does not start paid work. Do not work around such a failure by guessing a repository from ticket prose, changing CWD, or using an operator checkout.

A reviewer may ask the same bounded information question only while holding that exact ticket's live review lease and using its ordinary `board:read` + `board:review` scopes. Central must reject cross-ticket, expired, or foreign reviewer leases; this path grants neither board-write nor coordinator authority. Context-error reports carry a stable per-ticket idempotency key and a sanitized known message, so retries cannot create duplicate coordinator questions or disclose ticket-controlled exception text. If question reporting fails, the runner durably records the error and still uses Central's canonical human-hold/release APIs; reporting failure must not invoke the paid model or strand a review lease.

Code review requires an exact submitted candidate identity (branch and full commit SHA) in canonical submission evidence. A legacy submission without it fails closed as `submitted_candidate_missing`; reviewers must not infer a branch/SHA from annotations or select a convenient commit. The runner reports that bounded cause and requests a human hold so the submission owner/Butler can republish the candidate through the supported workflow. Only retry review after the corrected canonical submission is available and the registered protected clone contains its exact commit. Existing candidate/worktree data remains untouched during diagnosis.

## Canonical fleet worktrees

Given the registered protected clone (for example, `fleet/clones/pursers-sonar-ado`), the fleet worktree namespace is its path relative to the configured clone root under the sibling `fleet/worktrees` directory. A worker ticket uses the stable ticket ID as its canonical workspace directory and normally `pursers/<ticket-id>` as its branch. For compatibility, an already registered exact `<protected-clone>/.worktrees/<ticket-id>` workspace may be resumed when its branch is non-detached and ticket-bound (the ticket ID occurs in the branch); its existing branch name and dirty state are preserved. Ambiguous exact matches, detached work, suffix/diagnostic worktrees, symlink escapes, and branches not bound to the ticket are not candidates. A reviewer uses a separate ticket-and-submitted-SHA-specific detached worktree for the exact submitted candidate.

Worktree membership and Git common directory, origin, branch, ticket identity, and (for reviewers) submitted SHA are verified before context is passed to the model. A missing worker worktree is provisioned in the canonical namespace from the project's registered integration ref in a new ticket branch. Review worktrees use only the exact submitted commit already available in the registered clone. Existing worktrees are never reset or cleaned: worker dirty/untracked changes and commits are preserved and disclosed in context. Review candidate worktrees must be clean and at the submitted SHA. Symlink escapes, wrong repository/branch, stale or unavailable candidate commits, and malformed identities block safely; inspect and repair the registered workspace rather than deleting or replacing it.

## Recovery and scope

Fresh events, a still-owned lease, and restart recovery all repeat current Central authorization and Git/workspace verification before launch. Recovery may resume only the matching live lease epoch; expired, foreign, or stale events do not authorize work. Registry data passed to a model is bounded to the resolved board/project, repository identity, exact worktree/branch, and preservation state—not the full registry or ticket collection.

Workers may continue authorized owned fixes, tests, formatting/lint, and scoped submission. For an ordinary technical blocker, ask the configured authorized Butler a concrete information question with the error and inspected references; a human hold is for genuinely missing domain/authority facts or exhausted no-progress recovery. Reviewers independently compare the exact immutable base and submitted candidate, distinguish unchanged baseline findings from introduced/owned defects, do not modify candidate code, and report scoped acceptance separately from final combined QA.

Tests use temporary Git repositories and fake model captures only. Never use live customer services, credentials, or paid provider calls to validate event-context routing.
